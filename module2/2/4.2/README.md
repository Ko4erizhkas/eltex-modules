# 4.2 — Очередь с приоритетом

Очередь сообщений, где у каждого сообщения есть приоритет от 0 до 255.
Извлечь сообщение можно тремя способами: первое в очереди, с точно указанным
приоритетом и с приоритетом не ниже заданного. Тестовая программа генерирует
сообщения со случайными приоритетами и показывает все три выборки.

## Сборка и запуск

```
make
./pqueue.exe
```

Аргументов нет: программа сама создаёт 10 сообщений. Вывод в консоли — UTF-8,
`main.c` переключает кодовые страницы, поэтому программа привязана к Windows.

## Файлы

| Файл | Назначение |
|---|---|
| `pqueue.h` | Типы `Message`, `PQNode`, `PQueue` и API очереди |
| `pqueue.c` | Добавление, три вида извлечения, вывод, освобождение |
| `main.c` | Генерация сообщений и демонстрация выборок |
| `tests/` | Юнит-тесты на Unity |

## Модель данных

```
PQueue                 — очередь (head, size)
  └── PQNode           — узел (next, data)
        └── Message    — сообщение (text, priority)
```

Односвязный список, отсортированный по убыванию приоритета. Сообщение лежит
в узле по значению: одна аллокация на сообщение, `free(node)` освобождает всё
разом.

Сортировка выполняется при вставке, а не при извлечении. Плата — O(n) на
добавление, зато «первое в очереди» — это просто голова списка, а «не ниже
заданного» останавливается на первом же подходящем узле.

| Операция | Сложность | Описание |
|---|---|---|
| `pq_push` | O(n) | Спуск до места по приоритету и вставка |
| `pq_pop` | O(1) | Снятие головы списка |
| `pq_pop_priority` | O(n) | Первый узел с точно таким приоритетом |
| `pq_pop_atleast` | O(n) | Первый узел с приоритетом не ниже заданного |

## Порядок и живая очередь

Новый узел встаёт **после** уже имеющихся с равным приоритетом:

```c
while (*link && (*link)->data.priority >= priority)
    link = &(*link)->next;
```

Знак `>=`, а не `>`, поэтому внутри одного приоритета сохраняется живая
очередь: кто раньше пришёл, тот раньше уйдёт. Так же ведут себя и выборки —
`pq_pop_priority` и `pq_pop_atleast` берут первый подходящий узел, а не любой.

Из-за сортировки `pq_pop_atleast(0)` делает ровно то же, что `pq_pop`, — это
видно в примере ниже.

## Указатель на указатель

Все три извлечения обходят список через `PQNode**` — указатель на поле `next`
предыдущего узла (для первого узла это `&pq->head`):

```c
for (link = &pq->head; *link; link = &(*link)->next)
    if ((*link)->data.priority == priority)
        return pq_extract(pq, link, out);
```

Поэтому удаление из середины и удаление головы — один и тот же код, отдельный
случай для головы и хранение предыдущего узла не нужны. Всё снятие узла
сосредоточено в `pq_extract`.

## Соглашения API

| Правило | Поведение |
|---|---|
| Приоритет вне 0..255 | `pq_push` возвращает 0, очередь не меняется |
| `text` или очередь `NULL` | `pq_push` возвращает 0 |
| Текст длиннее `MAX_TEXT` | обрезается по `snprintf`, завершающий ноль на месте |
| Нет подходящего сообщения | `pq_pop*` возвращают 0, `out` не трогается |
| `out == NULL` | сообщение удаляется, содержимое не копируется |
| `pq_free` | освобождает узлы и саму очередь, обнуляет указатель |

## Пример работы

```
Генерация 10 сообщений:
   приоритет 198 | Служба журналирования #1
   приоритет  61 | Служба журналирования #2
   приоритет  24 | Служба журналирования #3
   приоритет 102 | Пользовательский запрос #4
   приоритет 250 | Пользовательский запрос #5
   приоритет  60 | Пользовательский запрос #6
   приоритет  90 | Датчик температуры #7
   приоритет  53 | Пользовательский запрос #8
   приоритет 123 | Служба журналирования #9
   приоритет 206 | Пользовательский запрос #10

Очередь (10 шт.):
 1) приоритет 250 | Пользовательский запрос #5
 2) приоритет 206 | Пользовательский запрос #10
 3) приоритет 198 | Служба журналирования #1
 4) приоритет 123 | Служба журналирования #9
 5) приоритет 102 | Пользовательский запрос #4
 6) приоритет  90 | Датчик температуры #7
 7) приоритет  61 | Служба журналирования #2
 8) приоритет  60 | Пользовательский запрос #6
 9) приоритет  53 | Пользовательский запрос #8
10) приоритет  24 | Служба журналирования #3

Выборка:
Первое в очереди: приоритет 250 | Пользовательский запрос #5
С приоритетом 60: приоритет  60 | Пользовательский запрос #6
С приоритетом 300: подходящих сообщений нет
С приоритетом не ниже 200: приоритет 206 | Пользовательский запрос #10
С приоритетом не ниже 0: приоритет 198 | Служба журналирования #1

Осталось в очереди (6 шт.):
 1) приоритет 123 | Служба журналирования #9
 2) приоритет 102 | Пользовательский запрос #4
 3) приоритет  90 | Датчик температуры #7
 4) приоритет  61 | Служба журналирования #2
 5) приоритет  53 | Пользовательский запрос #8
 6) приоритет  24 | Служба журналирования #3
```

Сообщения в очереди выстроены по убыванию приоритета, хотя приходили вразнобой.
Точный приоритет для второй выборки берётся из середины сгенерированного
набора, чтобы совпадение было гарантировано; приоритет 300 показывает отказ,
а «не ниже 0» — что после сортировки это то же самое, что «первое в очереди».
Приоритеты случайные, поэтому от запуска к запуску числа меняются.

## Тесты

```
cd tests
make test
```

Весь API `pqueue.c` публичный, поэтому файл линкуется как обычно, включать
`.c` в тест не требуется. Единственная функция с выводом — `pq_print`, для
неё `stdout` перехватывается в файл, а отчёт Unity уводится в `stderr` через
`unity_config.h`.

Покрыты: создание и освобождение (включая повторный вызов и `NULL`),
добавление (границы диапазона приоритетов, отказ вне диапазона и на `NULL`,
обрезка длинного текста), порядок в очереди и живая очередь внутри одного
приоритета, все три извлечения — из середины списка, первое из равных,
включающий порог у «не ниже», отказ при отсутствии подходящего сообщения с
сохранением размера очереди, `out == NULL`, — а также вывод очереди: пустая
очередь, `NULL` и порядок строк.
